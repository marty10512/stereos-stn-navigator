# Проверка условий договоров поставки — прототип

Локальный прототип для специалиста по закупкам: загружает TXT-документы (договоры, допсоглашения, письма), показывает по каждому договору сумму и срок поставки **по состоянию на дату проверки** и для каждого значения даёт проверяемое основание — файл, точную цитату и переход к абзацу исходника. Подписанные и вступившие в силу допсоглашения меняют условия; проекты и письма показываются отдельно как несогласованные предложения. Чего нет в документах — «нет данных», что нельзя разрешить надёжно — «нужна проверка».

Демо: https://marty10512.github.io/stereos-stn-navigator/ — кнопка «Загрузить пример» подгружает документы из `fixtures/documents/`.

## Установка и запуск

Зависимостей нет. Нужен только браузер; для тестов — Node.js 18+ (проверено на 22.14).

```bash
git clone https://github.com/marty10512/stereos-stn-navigator.git stn-navigator
cd stn-navigator
open index.html                          # macOS; в Windows — двойной клик по index.html
node --test                              # тесты
```

Страница работает с диска (`file://`), в сеть не обращается, ключей и платных сервисов не требует. Если браузер не открывает файл двойным кликом — `python3 -m http.server 8000` в папке проекта и http://localhost:8000.

## Пример использования

1. Открыть `index.html`. Дата проверки по умолчанию — 10.03.2026 (меняется в шапке).
2. Перетащить в окно все файлы из `fixtures/documents/` (или выбрать кнопкой; файлы можно добавлять в несколько заходов). На демо и через `python3 -m http.server` — кнопка «Загрузить пример»; с диска (`file://`) она скрыта, браузер не даёт странице читать соседние файлы. В `fixtures/variants/` — 12 документов того же формата с вариациями (другой формат номера, сумма прописью, «Срок поставки: до …», ДС «с момента подписания», неустойка рядом со стоимостью, CRLF и BOM); ожидаемое поведение по правилам ТЗ — `fixtures/variants/EXPECTED.md`, закреплено тестами.
3. Таблица «Договоры по состоянию на 10.03.2026»:

| Договор | Поставщик | Сумма | Срок поставки |
|---|---|---|---|
| STN-101 | ООО «Вектор Прибор» | 1 380 000 ₽ — изменено `02_amendment_signed.txt` (в силе с 01.03.2026), в договоре было 1 200 000 ₽ | 30.04.2026 — изменено тем же ДС, было 15.04.2026 |
| STN-102 | ООО «Контур Электро» | 840 000 ₽ | 20.03.2026; есть несогласованное предложение 27.03.2026 (письмо поставщика) |
| STN-103 | ООО «ПромСнаб Сервис» | нет данных — «Общая стоимость определяется спецификацией в приложении № 1» | 30.04.2026 |

   Клик по «Основание: …» открывает документ справа с подсвеченным абзацем и цитатой.
4. Блок «Вопросы» отвечает на четыре вопроса задания: срок по STN-101 на дату проверки — 30.04.2026; сумма STN-102 — 840 000 ₽; сумма STN-103 — нет данных; поставки раньше 01.04.2026 — только STN-102 (20.03.2026), и по нему есть несогласованное изменение срока (письмо, 27.03.2026).

Чтобы проверить, что ответы не вшиты: измените в `03_contract.txt` сумму или дату, загрузите файл заново — таблица и ответы пересчитаются. Новый договор того же формата (`ДОГОВОР ПОСТАВКИ № …`, `Статус: …`, пункты «Общая стоимость … составляет … рублей», «обязуется поставить … не позднее …») появится отдельной строкой.

## Как это работает

`core.js` — чистая логика без DOM (одна и та же в браузере и в тестах):

1. **Абзацы.** Текст делится на абзацы (непустые строки) с позициями — это адрес для перехода и цитаты.
2. **Документ.** По заголовку определяется тип (договор / допсоглашение / проект допсоглашения / письмо), по строке «Статус:» — подписан ли обеими сторонами, отдельно — дата документа, дата вступления в силу («вступает в силу 01.03.2026» или «с момента подписания»), ссылка на договор («К ДОГОВОРУ STN-101», «договор STN-102»).
3. **Поля.** Реестр `FIELDS` (`sum`, `deadline`) описывает для каждого поля четыре правила на уровне предложения: *отвлекающее упоминание* (аванс, лимит, неустойка, срок оплаты — пропустить), *явное отсутствие* («определяется спецификацией», «не установлен» → «нет данных» с цитатой), *действующая редакция* («Общая стоимость … составляет N рублей», «обязуется поставить … не позднее даты»), *изменение/предложение* («изменить … на N», «перенести срок … с X на Y»). Абзац допсоглашения «изложить в следующей редакции: «…»» разбирается теми же правилами — новая редакция повторяет формулировку договора.
4. **Сборка на дату.** К значениям договора применяются только подписанные ДС, у которых и дата подписания, и дата вступления в силу не позже даты проверки, по возрастанию даты вступления в силу; у поля появляются `changedBy` и исходное значение. Остальное (проект, письмо, подписанное ДС с будущей датой, ДС без подтверждённого статуса) — в `proposals`; в ответах подписанное, но ещё не действующее ДС называется так, а не «несогласованным предложением». Неоднозначности (несколько значений в договоре, два ДС на одну дату с разными значениями, неясный статус) → `needs_review` с пояснением.
5. **Вопросы.** `answer()` формулирует ответ из тех же полей и ссылается на те же основания.

Контракт данных между логикой и интерфейсом — `docs/schema.md`.

### Почему правила, а не LLM, и где граница

Документы одного жанра с устойчивыми формулировками; ответ должен быть детерминированным, воспроизводимым и проверяемым по цитате; у интервьюера не должно быть платных ключей. Правила дают это бесплатно и объяснимо: каждая строка таблицы — результат конкретного регулярного выражения на конкретном предложении, которое можно показать.

Граница: правила держатся на формулировках «общая стоимость … составляет», «обязуется поставить … не позднее», «изложить в следующей редакции», «вступает в силу». Договор в свободной форме, таблицы, спецификации, сроки «в течение 30 дней с даты оплаты», ДС, меняющее пункт без цитирования новой редакции, — распознаются частично или уходят в «нет данных» / «нужна проверка». Это честный отказ, а не выдуманное значение, но на разнородном корпусе покрытие правил упадёт; тогда LLM уместна как *извлекатель кандидатов с обязательной цитатой*, которую правила проверяют (см. улучшения).

## Известные ограничения

- Только TXT в UTF-8; PDF/DOCX/OCR вне объёма.
- Понимаются даты формата `ДД.ММ.ГГГГ` и суммы в рублях цифрами («1 380 000 рублей», «900000 руб.», «945 000,00 руб.»). Срок, заданный интервалом («в течение 30 дней с даты оплаты»), не вычисляется → «нужна проверка» с цитатой пункта. Две разные суммы или даты поставки в одном предложении (старая и новая редакция, две партии) → «нужна проверка».
- Статус подписания берётся из строки «Статус:» (или из фразы «подписано обеими сторонами» в тексте). Если его нет, ДС не применяется и поле помечается «нужна проверка».
- Привязка ДС и писем к договору — по явной ссылке на номер. Без неё документ попадает в список «не привязан».
- Ставка неустойки, предмет, порядок оплаты и прочие условия не извлекаются — реестр полей расширяется добавлением записи в `FIELDS`.
- Состояние живёт в памяти вкладки: перезагрузка страницы очищает загруженные файлы.

## Записка

**Для кого.** Специалист по закупкам, который перед решением (оплата, претензия, планирование склада) должен за минуту узнать действующую сумму и срок по договору и доказать это цитатой из подписанного документа, не перечитывая всю папку. Вторичный пользователь — юрист или руководитель, проверяющий его вывод по той же ссылке.

**Пять вопросов клиенту перед развитием.**
1. Откуда приходят документы (СЭД, почта, папка) и в каких форматах реально: сколько TXT против PDF и сканов?
2. Какие условия нужны следующими после суммы и срока — неустойка, аванс, предмет, гарантия, порядок приёмки — и кому из ролей что важно?
3. Как у вас фиксируется статус подписания: отдельная строка в документе, реестр в СЭД, подпись в PDF? Можно ли на него опираться автоматически?
4. Как часто встречаются конфликты (два ДС на одну дату, ДС без даты вступления в силу) и кто сегодня их разрешает?
5. Нужна ли история «как было на дату X» для аудита или достаточно текущего состояния?

**Допущения.** Условия меняет только подписанное обеими сторонами ДС, вступившее в силу к дате проверки; письма и проекты — информация для проверки. Один документ — один файл; договор определяется номером из заголовка; ДС и письма ссылаются на этот номер явно. Даты календарные, суммы в рублях. Имена файлов и порядок загрузки на приоритет не влияют.

**Две метрики.**
1. *Точность с основанием*: доля полей, где значение верно **и** цитата действительно его подтверждает (размечается выборкой; цель ≥ 95 %). Ошибки «значение верно, цитата не та» считаются ошибками — доверие строится на основании.
2. *Доля ручной проверки*: процент полей со статусом «нужна проверка» или «нет данных» при наличии данных в документе. Показывает, насколько правила покрывают реальный корпус; растёт при новых формулировках и подсказывает, что добавить.

**Архитектура.**

```
TXT-файлы ──▶ splitParagraphs ──▶ parseDocument (тип, статус, даты, ссылка на договор)
                                        │
                                        ▼
              FIELDS (правила на предложение: отвлекающее / отсутствие / редакция / изменение)
                                        │
                                        ▼
                  buildContract (договор + ДС по дате вступления в силу + предложения)
                                        │
                        ┌───────────────┴───────────────┐
                        ▼                               ▼
                 index.html (таблица,            answer() — ответы на
                 основания, просмотрщик)         вопросы с теми же основаниями
```

Один файл логики, один файл интерфейса, тесты на той же логике; никаких зависимостей, сервера и сборки.

**Три ключевых решения и компромиссы.**
1. *Правила вместо модели.* Плюс: детерминизм, бесплатно, цитата гарантирована (значение берётся из текста). Минус: покрытие ограничено формулировками; каждая новая форма — новое правило.
2. *Единица анализа — предложение, а не документ или пункт.* Плюс: ловушки («аванс составляет…», «срок оплаты, а не поставки», «лимит… не является стоимостью») отсекаются локально, и цитата получается точной. Минус: значение, разнесённое по двум предложениям или таблице, не собирается.
3. *Одна страница без сервера и зависимостей.* Плюс: запускается у любого интервьюера двойным кликом, нет версий и установки, та же логика гоняется тестами в Node. Минус: нет хранения и многопользовательской работы; текст целиком в памяти браузера.

**При 100 000 документов и правах доступа.** Разбор уходит из браузера в сервис с очередью и инкрементальной индексацией: документ разбирается один раз при поступлении, результаты (поля, цитаты, позиции) хранятся в БД, страница запрашивает уже посчитанное. Нужны: реестр договоров как сущность (а не группировка по номеру в памяти), версионирование состояния на дату, полнотекстовый индекс для поиска документов по договору, права — на уровне договора/контрагента/подразделения с фильтрацией результатов и цитат по ACL ещё в запросе, журнал кто что смотрел. Правила остаются, но получают конфигурацию под корпус клиента и метрику покрытия; ручная проверка становится очередью задач, а не бейджем.

**Три следующих улучшения.**
1. Расширить реестр полей: неустойка (ставка и потолок), аванс, предмет, срок оплаты — и показывать условие целиком, а не два поля.
2. Импорт PDF/DOCX с извлечением текста и привязкой цитат к страницам; без этого реальный корпус не загрузить.
3. LLM как второй извлекатель для нестандартных формулировок — только с обязательной цитатой, которую правила валидируют (цитата существует в тексте, число и дата из неё парсятся); расхождение правил и модели → «нужна проверка».

## Отчёт о вайбкодинге

**Инструмент.** Claude Code: основная сессия на Claude Fable 5.1, параллельные субагенты — Sonnet 5.5 (интерфейс) и Opus 5.5 (документы-ловушки, финальный ревью). Подробный журнал с временем — `WORKLOG.md`.

**Характерные запросы.**
1. Разбор задания до кода: «проанализируй задание, проведи ресерч, задай вопросы, подготовь план с моделями по этапам; без аппрува к разработке не приступай». Результат: эталонные ответы по шести документам, сравнение подходов и стеков, план; два решения остались за человеком — стек (JS без зависимостей) и способ сдачи.
2. Интерфейс по контракту данных: субагенту отдан `docs/schema.md` и семь блоков страницы с ограничениями (один файл, `file://`, без сети, классический `<script>`, только `textContent`) — чтобы UI писался параллельно с логикой и совпал по именам полей.
3. Адверсариальные документы: другому агенту — «сгенерируй 8–12 документов того же формата с вариациями, запиши ожидания по правилам ТЗ, прогони core.js, доложи расхождения с указанием места в коде» — чтобы заранее увидеть, что сломает «новый договор» на встрече.

**Ошибка ИИ и как поймана.** В первой версии `core.js` правила для русских слов были написаны через `\w` (`вступ\w+\s+в\s+силу`, `срок\w*`, `Дата(\s+\w+)?:`). В JavaScript без флага `u` класс `\w` не включает кириллицу. Поймано первым прогоном на учебных документах, а не чтением: у подписанного ДС к STN-101 дата вступления в силу вышла `null`, поля ушли в «нужна проверка» вместо 1 380 000 ₽ и 30.04.2026, у проекта ДС не распозналась «Дата проекта:». Исправлено заменой на явный класс `[а-яё]`, закреплено тестами на эти значения.
